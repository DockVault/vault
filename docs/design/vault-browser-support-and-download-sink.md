# Browser support, and where a streamed download is written

Two questions that have to be answered before a download can stop buffering the whole file: which
browsers this application supports, and where decrypted bytes go while they are being written.

Neither had an answer in this repository. There is no build step, no `browserslist`, and nothing in
the docs naming a supported browser — so the real floor has always been whichever modern API was
called without a guard, discovered when someone's upload failed. This file records the floor that
already exists, the floor a streamed download would add, and the choice of sink.

Every version below has a source. They were checked against browser-compat-data, caniuse, and the
engines' own bug trackers and release notes, because two of the numbers are wrong in the places
people usually read them.

---

## The floor that already exists

Nothing here is a new requirement. `Blob.arrayBuffer()` is the newest API the application already
calls without a guard, on both the upload and download paths.

| | Chrome | Edge | Firefox | Safari | Safari iOS |
|---|---|---|---|---|---|
| `Blob.slice` | 21 | 12 | 13 | 7 | 7 |
| **`Blob.arrayBuffer`** | **76** | **79** | **69** | **14** | **14.5** |

Source: [browser-compat-data `api/Blob.json`](https://github.com/mdn/browser-compat-data/blob/main/api/Blob.json).

The binding constraint is **iOS 14.5** (April 2021), a release later than desktop Safari 14
(September 2020). Below that line, a zero-knowledge upload has never worked.

An absent `Blob.arrayBuffer` is now reported as a browser capability rather than as bad input, so a
user on an old browser is told to upgrade instead of being told the operation failed.

## What a streamed download would add

The pattern: a service worker intercepts a same-origin URL and answers with a `Response` whose body
is a `ReadableStream`; the page decrypts chunks into that stream; the browser writes them to disk as
they arrive.

| | Chrome/Edge | Firefox | Safari | Safari iOS |
|---|---|---|---|---|
| Service worker responding to a fetch | 42 / 17 | 44 | 11.1 | 11.3 |
| **Service worker answering a DOWNLOAD with a streamed body** | long-standing | **58** | **15.4** | **15.4** |
| Transferable `ReadableStream` (an optimisation, not a requirement) | 87 | 103 | not in stable | not in stable |

Sources: [Bugzilla 1204254](https://bugzilla.mozilla.org/show_bug.cgi?id=1204254) (Firefox 58);
[WebKit r286944](https://trac.webkit.org/changeset/286944/webkit) and
[Safari 15.4 release notes](https://webkit.org/blog/12445/new-webkit-features-in-safari-15-4/)
(“support for allowing users to download files generated by a ServiceWorker”);
[browser-compat-data `api/ReadableStream.json`](https://github.com/mdn/browser-compat-data/blob/main/api/ReadableStream.json).

**No compat database records the middle row.** There is no key for “service worker answering a
download with a streamed body” anywhere in browser-compat-data; every number in it comes from an
engine's own bug tracker or release notes. Anyone re-checking this should expect to do the same.

Two numbers commonly quoted are wrong. Compat data lists Firefox 39 for constructing a `Response`
from a stream, inherited from the parent entry — `ReadableStream` itself is Firefox 65, so the
value is impossible. And the compat test only constructs the object and discards it; it never
enqueues a chunk or involves a service worker, so it certifies nothing about this pattern.

### Safari is not excluded

It was expected to be. It does not need to be.

The evidence usually cited for Safari being broken is a user-agent sniff in StreamSaver.js saying
it *“fails to download anything that comes from the service worker”*. That traces to an issue last
substantively updated in **June 2019** — two and a half years before WebKit implemented it — and has
never been revised. Excluding Safari on that basis would have been wrong.

What Safari genuinely lacks is transferable streams, which is an optimisation. Without them the page
posts chunks to the worker individually: no backpressure, and a keep-alive ping is required. Firefox
needs the same treatment below 103.

## The format is already the right shape — for new files only

The usual blocker for streaming decryption is that `SubtleCrypto` has no streaming interface, and
whole-file AES-GCM cannot authenticate a prefix: the tag covers the entire message, so nothing can
be released until everything has arrived. That is a file-format problem, not a browser one, and no
amount of browser support fixes it.

It does not apply to version-2 content. That format is already framed as independent per-chunk AEAD
records — the construction this pattern requires — and its reader already decrypts one record at a
time.

It **does** apply to every file written before that format. Legacy whole-file content keeps the
buffered path, and its size limit is a property of the file, not of the browser it is opened in.

## The unresolved part: where bytes go before they are trusted

The version-2 reader deliberately withholds output until the chunk marked final authenticates.
Releasing records as they verify would hand over output of attacker-chosen length and detect the
problem afterwards.

A service-worker download conflicts with that. Bytes written into the user's Downloads folder cannot
be withdrawn, so a file whose terminal record fails — truncated, tampered with, or interrupted —
leaves a partial artifact on disk that looks like a download that finished early.

Two ways to resolve it:

**A. Stream to the download, and accept a partial-output boundary.** Simplest, and the standard
pattern. The cost is that a failure is visible on disk, and the guarantee weakens from *nothing is
released until it authenticates* to *the user is told afterwards*.

**B. Stage in the origin private file system, then hand over the finished file.** Decrypt one chunk
at a time into OPFS, verify the terminal, and only then produce a download. Peak memory is one
chunk; peak disk is one file. The commit is atomic: a failed terminal deletes the staged file and
nothing reaches the user.

| | Chrome | Edge | Firefox | Safari | Safari iOS |
|---|---|---|---|---|---|
| OPFS `createSyncAccessHandle` | 102 | 102 | 111 | **15.2** | 15.2 |

Source: [browser-compat-data `api/FileSystemSyncAccessHandle.json`](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemSyncAccessHandle.json).

Two constraints that come with it. Sync access handles are **worker-only**, so the decrypt has to
run in a dedicated worker rather than on the page — which is where it belongs anyway. And the
staged file needs free disk of roughly the file's size until it is handed over.

The asynchronous alternative, `createWritable()`, is **not** a substitute: Safari only shipped it in
version 26, where the sync handle has been available since 15.2.

**Recommendation: B.** It keeps the property the format was designed around, it avoids every service
worker lifetime hazard listed below, and it is supported on a *lower* Safari version than the
service-worker path. What it gives up is the save dialog appearing at the start, and it needs free
disk for one file.

The File System Access API (`showSaveFilePicker`) is not a third option, and its absence is
permanent rather than pending. Mozilla's standards position calls the picker half of that API
harmful — *"we do not think meaningful end user consent is possible"* for cross-site access to a
local file system — while being explicit that it likes the storage half, which is why Firefox
shipped OPFS and not the picker. Safari has never shipped a picker either. Chrome on Android
nominally gained one in 132 but **cannot create new files with it**, only select existing ones, and
Android content URIs support no atomic rename. That leaves desktop Chromium, around a quarter of
traffic.

**This is the decision the design gate reserves for the owner**, because option A changes an
integrity property that the file format was built to provide.

## Hazards to design against

Ordered by how likely each is to be the thing that breaks.

- **Service worker termination mid-download.** Firefox terminates at 30 seconds idle and the bug to
  keep it alive during a response has been open since 2016
  ([1302715](https://bugzilla.mozilla.org/show_bug.cgi?id=1302715)); Firefox 102 broke the reference
  implementation in the field in exactly this way. A keep-alive ping is mandatory, not an
  optimisation. WebKit's own note on the download feature says the worker's lifetime is *not*
  extended — although its termination check short-circuits while a same-origin client exists, and
  the page producing the chunks is that client.
- **Chromium caps a fetch event at five minutes** even while streaming, and has declined to change
  it. A large download over a slow link exceeds that.
- **iOS reports a streamed download as 0 kB** with indeterminate progress
  ([WebKit 258412](https://bugs.webkit.org/show_bug.cgi?id=258412), open since June 2023). The file
  is correct; users read it as a failure and cancel.
- **`Content-Disposition` must contain `attachment`** or WebKit will not start the download, and a
  filename in the header overrides `<a download>`.
- **Scope and first load.** A worker served from a subdirectory cannot intercept a path above it
  without `Service-Worker-Allowed`, and without `clients.claim()` the first download after
  registration falls through to the network.
- **No resumability.** The URL-to-stream handle is one-shot, so a range re-request cannot be served.
- **Safari never cancels a download**, so a stream cancel will not release the server's side.
- Closing the tab ends the transfer in every engine. This is not a background download.
- **The buffered fallback fails hostilely, so check the size before allocating.** Chromium
  configures its allocators to *"prefer crashing rather than returning nullptr"*, so an oversized
  download tends to produce a dead tab rather than an exception. A size check against the
  platform's ceiling is worth more than a `try`/`catch` that never runs.

## Not established

- Whether the pattern behaves correctly on **current** Safari. The evidence that it was fixed in
  15.4 is strong; there is no evidence either way about today's stable, and it regressed once
  already in Safari 16. This needs one test on a real device before anything is built on it.
- Whether Safari's reported ~70-second limit on a fetch handler applies to a long-lived streamed
  **body**. The only public reproduction delays before returning the response, so it measures
  promise resolution rather than streaming.
- Per-tab memory limits on iOS. Developer reports suggest 1.5–3 GB before the page is reloaded;
  there is no primary source. For the buffered fallback, the documented limits that bind first are
  Chromium's in-memory blob cap of 2 GB on desktop and, far lower, **total physical memory ÷ 100 on
  Android** — five megabytes on a 512 MB device.
